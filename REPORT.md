# Отчёт: распределение дефицита

**Правило:** жёсткий приоритет между уровнями, пропорционально спросу внутри уровня; минимальная партия — через итеративное исключение; перегруз до кратности — только из остатка после всех уровней. Код: `allocator.py` (ядро ~120 строк).

## 1. Журнал решений

| Развилка | Что выбрали | Что отвергли и почему |
|---|---|---|
| **Приоритет или пропорция** | Жёсткий порядок между уровнями, внутри уровня — пропорционально спросу. Невзятое уровнем из-за кратностей уходит ниже. CASE_07: 100 / 0 / 0 | **Пропорция без приоритета** (≈ 83 / 8 / 8): подтверждённые заказы недополучают. **Веса 1/priority:** произвольны, не обосновать перед бизнесом. Для мягкого приоритета нужны квоты, их в данных нет |
| **Кратность и перегруз** | Основной проход — вниз до кратности, не больше спроса. Перегруз ≤ одной кратности и только из остатка после реального спроса **всех** уровней. CASE_01: 50 / 25 / 25 | **Никогда не превышать спрос:** 25 ед. лежат на заводе при непокрытых 45. **Вверх сразу:** 50 / 50 / 0, перегруз вытесняет спрос. **Флаг `allow_overship`:** второй режим без пользы |
| **Минимальная партия** | Эффективный минимум — наименьшее кратное `rounding` ≥ `min_lot`. Если доля меньше минимума, исключаем **одну** заявку (худшее «доля / минимум») и пересчитываем доли. После уровня возвращаем исключённых, если остатка хватает. CASE_02: 40 / 30 / 30 / 0 | **Жадно до спроса** (50 / 50 / 0 / 0): больше пустых полок. **Исключать всех недотянувших сразу:** 0 / 0 / 0 / 0 при 100 ед. на складе |
| **Ничьи** | Наибольший дробный остаток → больший спрос → `request_id`. Порядок строк не влияет. CASE_04: лишние единицы у R-401 и R-402 | **Порядок строк:** план меняется от перестановки строк. **Random с seed:** детерминирован, но необъясним |
| **Некорректные данные** | Однозначное чиним с предупреждением (`rounding_value = 0` → 1), прочее — карантин: 0 и причина, остальные заявки считаются. Валидация внутри `allocate` — требования соблюдаются и при прямом вызове | **Падать:** одна запись останавливает ночной расчёт. **Чинить по догадке** (−10 → 10): план на выдуманных данных |

## 2. Что не так в данных и в постановке

**Данные** (как поступили — в журнале):
- CASE_03: R-301 `demand = 0` → 0, это не ошибка; R-302 `demand = −10` → карантин (возврат, сторно или ошибка выгрузки — неизвестно); R-304 `rounding_value = 0` → 1.
- CASE_06: R-602 `min_lot` 250 больше спроса и всего объёма → карантин; R-601 `min_lot` 30 не кратен 25 → реальный минимум 50.
- CASE_04: строки перемешаны. CASE_01, 05, 06: спрос не кратен `rounding`.

**Постановка:**
- Не определены смысл `priority`, KPI плана, тип `demand_qty` (вопросы ниже) и поведение на некорректных данных (журнал). Решения приняты по допущению «минимум пустых полок».
- «Кейсы независимы» верно для CSV, но не для модуля: уровни сети и периоды связаны (разделы 5–6).

## 3. Три вопроса аналитику

1. **По какому KPI оценивается план:** fill rate в штуках, число обнулённых точек, OTIF ключевых клиентов, стоимость логистики? Ответ разворачивает три развилки: приоритет, `min_lot`, перегруз.
2. **Что означает `priority`:** тип потребности (заказ / прогноз / страховой запас) или важность клиента? Можно ли обнулять низшие уровни? Если нельзя — нужен fair share по квотам: другая структура алгоритма и другие входные данные.
3. **`demand_qty` — чистая потребность или валовая?** При валовой РЦ с полным складом получает столько же, сколько пустой: меняется база пропорции (спрос или дни покрытия).

## 4. Границы применимости

- **Пропорция награждает завышенный спрос.** РЦ просят 60 и 180 при равной потребности → 25 / 75. Всем выгодно завышать заявки. Лечится базой пропорции (вопрос 3).
- **Крупная кратность — лотерея.** Три РЦ по 100, паллета 100 → 100 / 0 / 0 по `request_id`, и каждый период выигрывает один и тот же РЦ. Лечится ротацией тай-брейка или учётом накопленного недовложения.
- **Исключение по `min_lot` бьёт по крупному РЦ.** РЦ 100 с `min_lot` 60 и два по 50 → 0 / 50 / 50: у крупного худшее «доля / минимум».
- **Перегруз «на одну кратность» бывает огромным.** Спрос 1 при кратности 100 → 100. Для дорогого или скоропортящегося товара нужен относительный допуск (≤ N% спроса).

## 5. Масштаб: 5 млн кейсов

- **Замер (1 поток):** кейс до 10 заявок — 60 мкс (~5 мин на 5 млн), до 100 заявок — 1.3 мс (~1.8 ч). Средний кейс окно не ломает.
- **Хвост:** исключение по `min_lot` квадратичное, 2000 заявок — 6.4 с. Порядок исключения по `demand / eff_min` при пересчёте не меняется (меняется только общий знаменатель), значит хватает одной сортировки: O(n log n). Плюс целочисленная арифметика вместо `Fraction`.
- **Параллелизм — по позициям, а не по кейсам:** внутри позиции уровни сети и периоды считаются последовательно. Пул процессов, пачки позиций; детерминизм сохраняется — у `allocate` нет общего состояния.
- **Ввод-вывод:** вместо `print` — коды причин и пакетная запись; ночью пересчитываются только изменившиеся позиции.

## 6. Многопериодность

**Почему жадность плоха.** Период 1: 100 ед., только заявка P3 на 100. Период 2: поставки нет, приходит P1 на 100. Жадно P3 = 100, P1 = 0: порядок «время, потом приоритет» ломает приоритет между периодами. Перекосы одной операции (тай-брейк, округление, `min_lot`) копятся у одних и тех же точек, а перенесённый спрос низших приоритетов может голодать бесконечно.

**Что делать:**
1. **Сначала приоритет, потом время:** приоритет 1 — на весь горизонт, приоритет 2 — на оставшийся кумулятивный объём и т. д. (как Capable-to-Match). `allocate` не меняется, ей передаётся `budget` за вычетом резерва высших приоритетов.
2. **Справедливость за горизонт:** пропорция по накопленному недовложению, тай-брейк по накопленному fill rate.
3. **Старение долга:** перенесённый спрос повышает приоритет через k периодов.
4. **LP/MIP как эталон** для контроля качества эвристики на выборке позиций.
